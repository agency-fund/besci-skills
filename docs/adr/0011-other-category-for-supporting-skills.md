# The `other` stage holds supporting skills, which are plain skills

Several skills end in a written report, and each was left to choose its own prose register. The first skill that needed a shared answer was `analyze-qualitative-themes`, whose report is meant to be read as research writing. A writing skill is not a behavioral-science method. It is a named step in none of the canonical sources, it belongs to no stage of a project, and the library's spec was not written for it: it has no evidence base to scan, no specialist to escalate to, and no output template a reviewer could judge a run by. Until now the `other` stage was a place to park a skill that fit nowhere: the validator warned on it, and the site filed anything in it under "Meta-skills".

**`other` is the stage for supporting skills.** A supporting skill is not a behavioral-science method. It does a job that the outputs of many skills share, such as writing. The first is `write-in-academic-voice`, which skills that produce a report can name. Others may follow, and they need not be about behavioral science at all. A supporting skill declares `type: supporting` and `stage: other`. Meta-skills also declare `other`, as before; an atomic skill never does.

**A supporting skill is a plain skill.** It meets the Agent Skills specification and nothing more of ours: a `SKILL.md` with a `name` that matches the folder and a `description`, written in whatever shape suits it. The eight sections, the trigger-rule clauses, the verb-first name, the test cases, the reference files, the evidence scan, `tested_in`, `produces`, the shared voice block, the changelog, and the inclusion tests do not apply. A skill written elsewhere can be carried as it is.

**What it still carries.** The catalog and the site need to know what a skill is, so a supporting skill has a `license` and the same `metadata` every skill has: `type`, `stage`, `version`, `status`, `authors`, and `org`. The limits on file types and sizes apply, and a file that `SKILL.md` points to must exist.

**Each supporting skill is listed in `docs/canonical-sources.md`**, under "Supporting skills", with the reason the library carries it and whose practice it is. Because no rule of the spec screens these skills, the list is the only gate: it is what keeps the stage from becoming a place for anything. Adding a row is a change to that page, so it needs agreement from maintainers of both organizations, like any other change to it.

**The validator checks the pairing and the list.** `type: supporting` with any stage but `other` is an error, and so is `type: atomic` with `stage: other` (E013). W013 fires on a supporting skill the list does not name. A bundled copy of the validator, which cannot see the page, stays silent on the list.

**The site shows them as their own group, and shows only the skill.** The catalog, the map, and the workflow builder show "Other" as a group after the seven stages, separate from "Meta-skills". A supporting skill's page has the skill's text and the reviews tab. It has no test-case, reference, or version-history tabs and no "takes in, produces" diagram, because the skill has none of those. The home page's stage chart keeps the seven stages, because a supporting skill is not a point in a project.

**Consequences.** `taxonomy.yaml` gains the type `supporting` and describes `other` as its stage. The spec (section 1, the `metadata.type` and `metadata.stage` rows, and a new section 13), `docs/taxonomy.md`, `CONTEXT.md`, the skill-creator's checklist, and the navigator's stage file say the same. A supporting skill can be named in another skill's closing, or in its procedure, like any library skill; the rule that a named skill must exist (E056) covers it. A skill that names a supporting skill should still work when installed alone, so it says what to do when the supporting skill is absent. `besci-skill-creator` and `besci-eval` are not for supporting skills: there is no spec to interview against and there are no test cases to run. This widens what the library carries beyond behavioral-science methods and exempts those skills from review against the spec, so it needs agreement from maintainers of both organizations before it is accepted.
